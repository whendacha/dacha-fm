# Meteor web bridge readiness — 2026-09-26

The web route `/mobile/auth` accepts the native app's 32-byte base64url PKCE challenge and random state, asks the mobile API for a NEP-413 challenge, signs the exact server message/nonce/recipient with Meteor, sends the resulting account ID/public key/signature to the API, and returns only the one-time code and original state to `dachafm://auth/callback`. The native app performs state validation and code exchange. The bridge never sends a bearer token in a URL or asks for a seed phrase, transfer, or contract access grant.

The adapter in `@near-wallet-selector/meteor-wallet@10.1.4` maps `signIn` to Meteor SDK `requestSignIn` with `ALL_METHODS` when no methods are given. The bridge therefore does not call `signIn`. It prepares the SDK and challenge first, then requires a separate tap that invokes `signMessage` before any await, preserving browser activation for Meteor's popup. The adapter forwards its optional account ID and the Meteor SDK accepts an absent ID. Cancel invalidates the attempt so late wallet or API responses cannot redirect the app. Whether Meteor's real iPhone wallet UX selects an account and approves that direct call still requires a device test. A successful browser build is not evidence of a real Meteor approval.

Configuration: set server-side `MOBILE_API_URL` to the HTTPS **origin** of the mobile API (no path) and `MOBILE_NEAR_NETWORK` to `mainnet` or `testnet`. Development permits an HTTP localhost API. The API itself requires `MOBILE_AUTH_DOMAIN`, `MOBILE_NEP413_RECIPIENT`, and `MOBILE_NEAR_RPC_URL`. An absent or invalid bridge/API configuration reports unavailability. Deploying the bridge at a real HTTPS origin and setting the native app's `MeteorBridgeURL` remain release requirements.

Checks run in `web`: `node --test src/app/mobile/auth/protocol.test.mjs` (3 passed), `tsc --noEmit` (passed), and final `next build` (passed, showing both bridge routes as dynamic). Tests cover malformed/duplicate inputs, nonce and expiry validation, and fixed callback destination. No live server challenge, Meteor wallet approval, iPhone `ASWebAuthenticationSession` callback, or end-to-end code exchange was verified because those require configured services and an actual wallet/device.
